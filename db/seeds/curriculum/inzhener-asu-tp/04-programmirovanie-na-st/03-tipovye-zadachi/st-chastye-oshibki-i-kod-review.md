## Ментальная модель: код-ревью — это узнавание конкретных ловушек, а не общая эрудиция

На собеседовании тебе почти наверняка покажут фрагмент кода и спросят: «что здесь не так?». Это не тест на знание синтаксиса — это проверка, видел ли ты раньше конкретные ловушки ST. Здесь — четыре самых частых, каждая с симптомом, причиной и починкой.

## Ошибка 1: сравнение REAL на точное равенство

```st
// ПЛОХО
IF level_m = 1.5 THEN
    pump_on := TRUE;
END_IF;
```

**Симптом:** условие почти никогда не срабатывает, хотя по расчётам значение должно было «дойти» ровно до 1.5.

**Причина:** `REAL`/`LREAL` хранят число в двоичной плавающей точке — большинство десятичных дробей (включая безобидные на вид `0.1` или результат деления `1.0 / 3.0 * 3.0`) физически **не представимы точно**. Значение, которое в логике «должно быть 1.5», на деле может оказаться `1.49999998` — и точное сравнение с `1.5` никогда не станет `TRUE`.

**Починка:** сравнивай с допуском:

```st
// ХОРОШО
IF ABS(level_m - 1.5) < 0.001 THEN
    pump_on := TRUE;
END_IF;
```

> [!ВАЖНО] Это касается **только** `REAL`/`LREAL`. Для `INT`, `DINT`, `BOOL`, `ENUM` точное сравнение (`=`) абсолютно нормально и ожидаемо — не переусердствуй, добавляя `ABS(...) < eps` туда, где сравниваются целые числа.

## Ошибка 2: гонка присвоений — порядок кода решает, кто победит

Это самая коварная ошибка из четырёх, потому что код выглядит логично, а ломается только в конкретном сценарии:

```st
// ПЛОХО — порядок веток решает исход, а не приоритет по смыслу
IF dry_run = FALSE THEN
    pump := FALSE;          // защита: нет воды — выключить насос
    alarm := TRUE;
END_IF;

IF level_m < 0.5 THEN
    pump := TRUE;            // авторежим: мало воды — включить насос
END_IF;
```

**Симптом:** защита от сухого хода периодически «не срабатывает» — насос всё равно включается.

**Причина:** ST выполняется сверху вниз **последовательно в пределах одного скана**, и в переменную можно писать несколько раз за скан — побеждает **последняя по порядку кода** запись, а не «более важная по смыслу». Если `level_m < 0.5` истинно **одновременно** с `dry_run = FALSE`, первый блок честно выставит `pump := FALSE`, но второй блок, стоящий ниже, тут же перезапишет её обратно в `TRUE` — защита физически не может сработать, потому что её присваивание не последнее.

**Починка:** защита должна быть **последней записью** в переменную за скан — либо переставь блок защиты в конец кода, либо перепиши логику с явным приоритетом:

```st
// ХОРОШО — защита пишет в pump последней и не может быть перезаписана
pump := FALSE;
IF level_m < 0.5 THEN
    pump := TRUE;
END_IF;
IF dry_run = FALSE THEN
    pump := FALSE;   // защита — самая последняя запись, ничего не перебьёт её после
    alarm := TRUE;
END_IF;
```

> [!ОПАСНО] Именно эта ошибка стоит за требованием «защита должна быть главнее любой другой логики», которое уже встречалось в практике про [управление насосом](/ru/lessons/programma-upravleniya-nasosom) и в [паттерне блокировок](/ru/lessons/st-tipovye-bloki-i-patterny). Здесь — механическая причина, **почему** это требование вообще нужно формулировать явно: без понимания «последняя запись побеждает» разработчик легко пишет код, где защита логически присутствует, но фактически не работает.

## Ошибка 3: CASE без ветки по умолчанию

```st
// ПЛОХО
CASE state OF
    State_Idle:   ...
    State_Dosing: ...
    State_Done:   ...
END_CASE;
```

**Симптом:** после сбоя (помеха, ошибка при чтении из сети, баг в другом месте кода) переменная `state` внезапно получает значение, не описанное ни одной веткой, — и `CASE` **молча ничего не делает** в этом скане. Выходы застывают в прежнем состоянии, будто программа зависла, хотя технически она продолжает работать.

**Починка:** всегда добавляй `ELSE` в критичный `CASE` — это твоя защита от неожиданного состояния:

```st
// ХОРОШО
CASE state OF
    State_Idle:   ...
    State_Dosing: ...
    State_Done:   ...
ELSE
    state  := State_Fault;   // неизвестное состояние — это авария, а не тишина
    dosing := FALSE;
END_CASE;
```

## Ошибка 4: переименование RETAIN-переменной сбрасывает её значение

**Симптом:** отработавший месяцами счётчик наработки вдруг обнулился после безобидного, казалось бы, рефакторинга — переименовал переменную или поменял её тип для ясности кода.

**Причина:** если меняется **имя или тип** объявления `RETAIN`/`PERSISTENT`-переменной, среда считает её новой переменной и инициализирует заново — старое сохранённое значение не переносится автоматически. Само по себе изменение **порядка** объявления без правки имени/типа значения не портит, но именно переименование и смена типа — типичный способ незаметно потерять накопленные данные, обновляя код на уже работающей машине. Подробности и инструменты безопасного управления такими списками — в [документации CODESYS](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_preserve_data_with_retain_variables.html).

> [!СОВЕТ] Перед обновлением кода на объекте, где есть важные `RETAIN`/`PERSISTENT` переменные (счётчики партий, наработка оборудования), сверься, не переименовал ли и не сменил ли ты тип ни одной из них — иначе накопленные месяцами данные обнулятся при следующей загрузке.

## Памятка для код-ревью

| Ошибка | Симптом | Починка |
|---|---|---|
| `REAL` на точное равенство | условие почти никогда не срабатывает | сравнение с допуском: `ABS(a - b) < eps` |
| Гонка присвоений | защита «срабатывает», но не помогает | защита — последняя запись в переменную за скан |
| `CASE` без `ELSE` | при сбое выходы «замирают» молча | всегда добавляй `ELSE` в критичный `CASE` |
| Переименование `RETAIN`-переменной | накопленное значение обнулилось после обновления | не переименовывай и не меняй тип уже работающих `RETAIN`/`PERSISTENT` |

## Мост к первоисточнику

Все четыре ошибки — не о незнании синтаксиса ST (его [ГОСТ Р МЭК 61131-3-2016](https://allgosts.ru/25/040/gost_r_mek_61131-3-2016) описывает однозначно), а о том, как код **на самом деле** исполняется: представление `REAL` в памяти, последовательное выполнение скана, поведение `CASE` с необработанным значением. Именно это отличает разработчика с опытом от того, кто выучил ключевые слова, — и именно это чаще всего спрашивают на практическом собеседовании.

> [!ПРОВЕРЬ]
> 1. Почему `IF x = 1.5 THEN` — плохая идея для `REAL`, и что писать вместо этого?
> 2. Два блока `IF` пишут в одну и ту же переменную `pump` в разных условиях — какой из них победит и почему?
> 3. Что произойдёт, если `state` примет значение, не описанное ни одной веткой `CASE` без `ELSE`?

## Задание

Возьми свою программу `FB_Dosator` из статьи про [типовые паттерны](/ru/lessons/st-tipovye-bloki-i-patterny) и проведи по ней код-ревью против всех четырёх ошибок этой статьи:

1. Есть ли в коде сравнение `REAL` на точное равенство? Если да — почини на сравнение с допуском.
2. Есть ли переменная, в которую пишут из нескольких веток `CASE` или `IF` — и важен ли порядок этих записей? Проверь явно.
3. Есть ли в твоём `CASE` ветка `ELSE` на случай неожиданного состояния?
4. Если бы у `FB_Dosator` был `RETAIN`-счётчик выполненных циклов дозирования — на каком шаге рефакторинга кода ты рисковал бы случайно его обнулить?

Критерий самопроверки: пройдись по всем четырём пунктам письменно, даже если ответ «в моём коде такой ошибки нет» — обоснуй каждый ответ одним предложением, а не просто «да/нет».
