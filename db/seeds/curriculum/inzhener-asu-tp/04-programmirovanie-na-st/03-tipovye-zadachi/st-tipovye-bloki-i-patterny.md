## Ментальная модель: за разными задачами стоят одни и те же несколько паттернов

Дозатор, конвейер, насосная станция, линия розлива — на первый взгляд разные объекты. Но если разобрать логику каждого, под капотом почти всегда одни и те же несколько ходов: «объект проходит через ограниченный набор состояний», «прежде чем разрешить действие — проверь, что ничего не мешает», «одно нажатие кнопки не должно сработать 50 раз подряд, пока её держат». Выучи эти паттерны один раз — и на собеседовании задача «напиши логику для X» перестанет быть загадкой: ты будешь узнавать в ней уже знакомую форму.

## Готовые блоки сверх таймеров и счётчиков

[Таймеры и счётчики](/ru/lessons/taymery-schetchiki-tipovye-bloki) — не единственные стандартные блоки, которыми реально пользуются каждый день:

| Блок | Что делает | Типичное применение |
|---|---|---|
| **R_TRIG** | превращает `FALSE→TRUE` в импульс длиной ровно 1 скан | «сделай один раз на нажатие», а не «всё время, пока держат» |
| **F_TRIG** | то же для `TRUE→FALSE` | реакция на отпускание, на пропадание сигнала |
| **SEL(G, IN0, IN1)** | выбор из двух значений по булеву флагу `G` | переключение «ручной / авто» источник уставки |
| **MUX(K, IN0, IN1, IN2…)** | выбор одного из нескольких значений по числовому индексу `K` | выбор рецепта/пресета из списка |
| **LIMIT(MN, IN, MX)** | обрезает `IN` до диапазона `[MN, MX]` | не дать расчётной уставке выйти за безопасный диапазон оборудования |

> [!ПРИМЕР] **Детекция фронта — без неё код срабатывает не так, как ты думаешь.** Кнопка квитирования аварии `ack_btn` физически удерживается человеком доли секунды — но это может быть **несколько сканов подряд**. Простой `IF ack_btn THEN alarm_active := FALSE; END_IF;` выполнится на каждом скане, пока кнопка нажата, — обычно не страшно для одной булевой переменной, но становится багом, если это должно случиться **ровно один раз** (например, увеличить счётчик или отправить импульс в другую систему). Решение — `R_TRIG`:
> ```st
> ack_trig : R_TRIG;
> ...
> ack_trig(CLK := ack_btn);
> IF ack_trig.Q THEN
>     alarm_active := FALSE;   // сработает ровно один скан на одно нажатие
> END_IF;
> ```

## Паттерн 1: стейт-машина на CASE

Это главный паттерн этой статьи — большинство последовательной логики на объекте укладывается в **конечный автомат**: набор состояний и условий перехода между ними. Возьмём `E_DosatorState` (`State_Idle`, `State_Dosing`, `State_Done`, `State_Fault`) из [статьи про перечисления](/ru/lessons/st-massivy-struktury-perechisleniya) и опишем тело `FB_Dosator`:

```st
CASE state OF
    State_Idle:
        dosing := FALSE;
        ready  := TRUE;
        IF start THEN
            state := State_Dosing;
        END_IF;

    State_Dosing:
        ready  := FALSE;
        dosing := TRUE;
        IF current_kg >= target_kg THEN
            state := State_Done;
        END_IF;

    State_Done:
        dosing := FALSE;
        state  := State_Idle;

    State_Fault:
        dosing := FALSE;
        ready  := FALSE;
        // выход только явным квитированием — см. паттерн 3
END_CASE;
```

Почему именно `CASE`, а не дерево из вложенных `IF`? Потому что в каждый момент времени активна **ровно одна ветка**, и добавление нового состояния — это ещё одна секция `CASE`, а не переплетение условий с существующими. Через полгода коллега, открыв код, за 10 секунд поймёт, в каких состояниях вообще бывает объект — просто прочитав список меток `CASE`.

Загрузи это тело в `dos1` и открой тот же watch-лист, что собирал в статье про [CODESYS на практике](/ru/lessons/codesys-proekt-pou-i-otladka), — `dos1.state` до этого стоял на месте, потому что логики не было. Теперь он начнёт переключаться по мере того, как ты форсируешь `start` и `current_kg`.

## Паттерн 2: блокировки и пермиссивы

Прежде чем разрешить команду, собери **все условия, которые должны быть истинны**, в одну переменную-разрешение — вместо того чтобы разбрасывать проверки по всему коду:

```st
allow_start := NOT e_stop AND door_closed AND NOT overheat AND air_pressure_ok;

IF allow_start AND start_btn THEN
    running := TRUE;
END_IF;
```

Так на объекте видно **одной строкой**, что вообще может помешать пуску — не нужно перечитывать всю программу в поисках разбросанных условий.

> [!ВАЖНО] Приоритет защит всегда выше приоритета команд управления — тот же принцип, что и в защите от сухого хода в [практике про насос](/ru/lessons/programma-upravleniya-nasosom): аварийное условие обязано перебивать любую команду «включить», независимо от режима и от того, кто и что нажал. Пиши защиту так, чтобы она физически не могла быть обойдена веткой логики ниже по коду.

## Паттерн 3: квитирование аварий

Авария — это не просто «булева переменная стала TRUE». Правильное поведение: авария **фиксируется** (защёлкивается) в момент возникновения причины и **не снимается сама**, даже если причина исчезла, — пока оператор явно не квитирует:

```st
fault_trig : R_TRIG;
...
IF overheat OR dry_run_fault THEN
    fault_active := TRUE;        // защёлкнулась
END_IF;

fault_trig(CLK := ack_btn);
IF fault_trig.Q AND NOT overheat AND NOT dry_run_fault THEN
    fault_active := FALSE;       // снимается только по нажатию И при устранённой причине
END_IF;
```

Такое поведение называют **бистабильным элементом с приоритетом сброса или установки** (в стандартной библиотеке есть готовые блоки `SR`/`RS` именно для этого — «set dominant» и «reset dominant» защёлки), но собрать его вручную из `R_TRIG` и пары условий, как выше, — тоже нормальная практика, когда логика квитирования не тривиальна (как здесь — сброс требует ещё и отсутствия причины).

## Мост к первоисточнику

Все эти блоки — `R_TRIG`, `F_TRIG`, `SEL`, `MUX`, `LIMIT`, `SR`/`RS` — определены в [ГОСТ Р МЭК 61131-3-2016](https://allgosts.ru/25/040/gost_r_mek_61131-3-2016) как часть стандартной библиотеки, доступной в любой МЭК-совместимой среде под одинаковыми именами. Паттерны (стейт-машина, блокировки, квитирование) стандартом не описаны — это отраслевая практика поверх него, но именно она составляет содержание практического собеседования сильнее, чем синтаксис языка.

> [!ПРОВЕРЬ]
> 1. Почему `IF ack_btn THEN ... END_IF` без `R_TRIG` может сработать не один раз, а несколько сканов подряд?
> 2. Зачем собирать все условия разрешения пуска в одну переменную `allow_start`, а не проверять их по отдельности в разных местах кода?
> 3. Почему авария должна защёлкиваться, а не сбрасываться автоматически, как только пропала причина?

## Задание

Допиши тело `FB_Dosator` (декларацию ты уже сделал в задании статьи про [FUNCTION_BLOCK](/ru/lessons/st-function-function-block-program)) полной стейт-машиной:

1. `State_Idle` → `State_Dosing` по `start` (только если `allow_start`, собранного из `NOT e_stop` и `hopper_not_empty` — придумай сигналы сам).
2. `State_Dosing` → `State_Fault`, если `current_kg` превысил `target_kg` больше чем на 5% (переполнение — типичная авария дозатора).
3. `State_Fault` квитируется по нажатию `ack_btn` (через `R_TRIG`) только если причина аварии уже неактуальна.
4. Опиши, как `allow_start` должен учитывать `State_Fault` — можно ли стартовать дозатор, пока он в аварии?

Критерий самопроверки: нарисуй на бумаге диаграмму состояний (кружки + стрелки с подписанными условиями) по своему коду и сверь, что каждая стрелка в коде и на бумаге совпадает.
