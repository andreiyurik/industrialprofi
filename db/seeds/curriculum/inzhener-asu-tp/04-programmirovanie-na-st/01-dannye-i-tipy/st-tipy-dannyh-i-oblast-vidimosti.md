## Ментальная модель: переменная — это контракт, а не просто ячейка

В [первой статье про ST](/ru/lessons/structured-text-st) ты объявлял `BOOL`, `INT`, `REAL` и `TIME` — и этого хватало для простых задач. Но каждая переменная в ST — это не только тип данных, а ещё и **контракт**: кто её может менять, где она живёт, переживёт ли перезапуск контроллера. Забыл о контракте — получил переменную, которая либо занимает память зря, либо (хуже) обнуляется именно тогда, когда обнуляться не должна: счётчик отгруженных партий слетел после планового рестарта ПЛК на выходных.

## Полный набор элементарных типов

Базовых `INT`/`REAL`/`BOOL`/`TIME` мало для промышленной задачи. Вот расширенный набор, который реально встречается в проектах:

| Тип | Диапазон / хранит | Типичное применение |
|-----|--------------------|----------------------|
| `SINT` / `USINT` | −128…127 / 0…255 | компактный счётчик, номер режима из небольшого списка |
| `INT` / `UINT` | −32768…32767 / 0…65535 | сырое значение с AI-модуля, обычный счётчик |
| `DINT` / `UDINT` | ±2,1 млрд / 0…4,3 млрд | большие счётчики (наработка в секундах), Modbus-регистры на 32 бита |
| `REAL` | ~7 значащих цифр | инженерные величины: температура, давление, уровень |
| `LREAL` | ~15 значащих цифр | точные расчёты (например, накопление за смену без потери точности) |
| `BOOL` | TRUE/FALSE | дискретный сигнал, флаг |
| `STRING` | текст (по умолчанию 80 символов) | имя рецепта, код ошибки текстом, серийный номер |
| `TIME` | интервал | уставки таймеров: `T#5S` |
| `DATE` / `TOD` / `DT` | дата / время суток / дата+время | штамп события, расписание |
| `BYTE` / `WORD` / `DWORD` | 8 / 16 / 32 бита без знака | битовые маски, «сырые» слова из протокола (Modbus-регистр целиком) |

> [!ВАЖНО] `WORD`/`DWORD` — это **не число**, а набор бит. Их используют, когда нужно разложить регистр на отдельные флаги (например, слово статуса частотника, где бит 0 — «пуск», бит 3 — «авария»), а не для арифметики. Для арифметики бери `INT`/`DINT`/`REAL`.

## Область видимости: где живёт переменная

Тип отвечает «что хранит», область видимости — «кто видит и что переживёт». Это разные вопросы, и в CODESYS у них своя декларация:

| Секция | Где видна | Типичное применение |
|--------|-----------|----------------------|
| `VAR` | только внутри своего POU | локальный счётчик цикла, промежуточный расчёт |
| `VAR_INPUT` | входной параметр блока, пишет вызывающий код | «дай мне уровень, я решу — открывать клапан или нет» |
| `VAR_OUTPUT` | выходной параметр блока, читает вызывающий код | результат расчёта, готовый к использованию снаружи |
| `VAR_IN_OUT` | и вход, и выход одной переменной (передаётся по ссылке) | блок изменяет структуру/массив, переданный ему напрямую |
| `VAR_GLOBAL` (в [GVL](/ru/lessons/codesys-proekt-pou-i-otladka)) | во всём проекте | режим линии, общие уставки, флаг «авария всей линии» |
| `VAR_EXTERNAL` | ссылка на глобальную переменную из другого POU | используешь глобальную переменную, но не хочешь дублировать её декларацию |
| `CONSTANT` (модификатор) | значение нельзя менять из кода | `MAX_TEMP_C : REAL := 90.0; CONSTANT` вместо магического числа `90.0`, раскиданного по всей программе |

> [!ПРИМЕР] **Три переменные — три разных требования к «памяти».** Пищевой цех, линия розлива:
> - `local_step : INT` — шаг текущего цикла разлива одной бутылки. Живёт только пока выполняется POU, после — не нужен. Обычный `VAR`.
> - `total_bottles_shift : DINT` — счётчик бутылок за смену. Плановый **тёплый рестарт** (перезапуск программы без выключения питания) не должен его обнулять — нужен `RETAIN`.
> - `total_bottles_lifetime : LREAL` — общий счётчик с момента ввода линии в эксплуатацию. Должен пережить даже **перезагрузку проекта и обновление прошивки** — здесь нужен `RETAIN PERSISTENT` (просто `PERSISTENT` без `RETAIN` в CODESYS для этого не используют).

> [!ОПАСНО] `RETAIN` переживает тёплый рестарт, но **не** переживает холодный старт, повторную загрузку (download) или обновление прошивки — значение молча обнулится. Если счётчик критичен для учёта или безопасности (партии, наработка, счётчик циклов клапана до техобслуживания) — используй `RETAIN PERSISTENT`, а не просто `RETAIN`, и проверь поведение на реальном контроллере: детали различаются по вендорам, сверяйся с [документацией CODESYS](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_var_persistent.html).

> [!СОВЕТ] Заведи себе единый префикс переменных и держись его во всех проектах: `b_` — BOOL, `i_`/`di_` — INT/DINT, `r_`/`lr_` — REAL/LREAL, `st_` — [структура](/ru/lessons/st-massivy-struktury-perechisleniya), `a_` — массив (например, `b_pump_run`, `r_level_m`). Это не требование стандарта, а негласный отраслевой обычай CODESYS-разработчиков — код с префиксами читается по имени переменной без похода к декларации, и на собеседовании умение объяснить свой стиль именования выделяет тебя на фоне «просто написал код, который работает».

## Мост к первоисточнику

[ГОСТ Р МЭК 61131-3-2016](https://allgosts.ru/25/040/gost_r_mek_61131-3-2016) выглядит как сухой перечень типов — но именно в нём зафиксированы точные диапазоны и правила совместимости типов между собой (например, нельзя без явного преобразования присвоить `REAL` переменной значение `INT` — компилятор CODESYS на это ругнётся). Раздел «Элементы языка» стоит открыть один раз и свериться: какие типы вообще существуют в стандарте, а какие — расширение конкретного вендора (например, `LWORD` есть не везде). Это тот случай, когда 10 минут с документом экономят час недоумения «почему код не компилируется на другом контроллере».

> [!ПРОВЕРЬ]
> 1. Чем `RETAIN` отличается от `RETAIN PERSISTENT` — и какую переменную выбрать для наработки насоса, которая должна выжить даже после замены прошивки?
> 2. Для чего нужна `VAR_IN_OUT`, если уже есть `VAR_INPUT` и `VAR_OUTPUT`?
> 3. Почему `90.0` прямо в коде — плохая практика, и как это лечится модификатором `CONSTANT`?

## Задание

Для линии упаковки распиши таблицу из 6 переменных: имя → тип → область видимости/модификатор → одно предложение обоснования.

1. Счётчик коробок в текущей пачке (обнуляется каждую пачку, локальный расчёт).
2. Общий счётчик коробок с момента ввода линии в работу (не должен теряться никогда).
3. Максимально допустимая температура нагревателя термоусадки — используется в нескольких местах кода, менять из программы не должна.
4. Скорость конвейера, вычисленная одним блоком и переданная другому для отображения.
5. Флаг «линия в аварии», который должны видеть все POU проекта одновременно.
6. Параметр «заданный уровень», который блок регулирования принимает на вход и не имеет права изменять сам.

Критерий самопроверки: сверь каждую строку с таблицей области видимости выше — если для пункта 2 ты выбрал просто `RETAIN` без `PERSISTENT`, найди в статье, почему это ошибка.
