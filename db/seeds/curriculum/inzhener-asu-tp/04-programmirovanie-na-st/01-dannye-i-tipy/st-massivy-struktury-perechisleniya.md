Массивы, структуры (STRUCT) и перечисления (ENUM) в Structured Text — как хранить данные о десятках однотипных приводов без сотни отдельных переменных.
---
Тип и [область видимости переменной](/ru/lessons/st-tipy-dannyh-i-oblast-vidimosti) — это про одну переменную. Эта статья — про то, как избежать сотен отдельных переменных вовсе.

## Ментальная модель: не плоди переменные — группируй их

Представь линию с 5 конвейерными приводами. Наивный путь — завести `motor1_speed`, `motor1_current`, `motor1_fault`, `motor2_speed`… и так до пятого. Двадцать переменных, ни одна логическая связь между ними не видна из кода, а если приводов станет 20 — задача превратится в ад копипаста. Правильный путь — **сгруппировать данные одного привода** в структуру и **размножить приводы** массивом структур. Это ядро того, что отличает читаемую промышленную программу от простыни переменных.

## Массивы (ARRAY): один тип, много экземпляров

```st
VAR
    speeds : ARRAY[1..5] OF REAL;        // скорости пяти приводов
    matrix : ARRAY[0..2, 0..2] OF INT;   // двумерный массив (реже, но встречается)
END_VAR

speeds[1] := 12.5;                        // обращение по индексу
```

Границы `[1..5]` задаются явно при объявлении и **не меняются в рантайме** — размер массива фиксирован (в отличие от списков в Python/JS). Индексация может начинаться с любого числа, но отраслевой обычай — с `1` для физического оборудования (привод №1, а не №0) и с `0` для чисто программных буферов.

> [!ОПАСНО] По умолчанию CODESYS **не останавливает программу** при выходе индекса за границы массива — обращение по несуществующему индексу молча **обрежется до ближайшей границы** (запись в `speeds[99]` при массиве `[1..5]` реально попадёт в `speeds[5]`), а не выдаст ошибку. Это тихий баг, который неделями сидит в коде, пока кто-то не заметит, что данные пятого привода необъяснимо путаются с шестым. Средство — добавить в проект объект «POU for Implicit Checks» → Bounds check (описано в [документации CODESYS](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_datatype_array.html)) и никогда не доверять индексу, посчитанному по формуле, без проверки диапазона.

## Структуры (STRUCT): группируем разнородные поля одного объекта

Структура — это пользовательский тип данных: пачка полей разных типов под одним именем. В CODESYS её объявляют отдельным объектом (DUT — data unit type), не внутри POU:

```st
TYPE ST_Motor :
STRUCT
    speed_hz   : REAL;    // текущая частота с ЧРП
    current_a  : REAL;    // ток двигателя
    running    : BOOL;    // подтверждение работы
    fault      : BOOL;    // авария привода
END_STRUCT
END_TYPE
```

Дальше `ST_Motor` — обычный тип, как `INT` или `REAL`. Можно объявить одну переменную (`motor_1 : ST_Motor;`) или сразу массив структур:

```st
VAR
    conveyors : ARRAY[1..5] OF ST_Motor;   // пять приводов, каждый — полный набор полей
END_VAR

conveyors[3].speed_hz := 25.0;              // точка = обращение к полю структуры
```

> [!ПРИМЕР] **Пять приводов — пять строк вместо двадцати переменных.** С `ARRAY[1..5] OF ST_Motor` весь конвейерный участок описан одной декларацией. Проверка «есть ли авария хоть на одном приводе» превращается в цикл по массиву структур (сам [цикл `FOR`](/ru/lessons/st-cikly-i-storozhevoy-taymer) разберём в следующей статье):
> ```st
> any_fault := FALSE;
> FOR i := 1 TO 5 DO
>     IF conveyors[i].fault THEN
>         any_fault := TRUE;
>     END_IF;
> END_FOR;
> ```
> Добавили шестой привод на линию — поменяли одну цифру в границе массива, а не переписали логику заново.

## Перечисления (ENUM): имя вместо магического числа

Вместо `mode : INT` со значениями `0`, `1`, `2`, смысл которых помнишь только ты (и то не всегда), заводят перечисление:

```st
TYPE E_LineMode :
    (Mode_Stop, Mode_Manual, Mode_Auto);
END_TYPE

VAR
    mode : E_LineMode := Mode_Stop;
END_VAR

IF mode = Mode_Auto THEN
    // логика автоматического режима
END_IF;
```

`Mode_Auto` читается сам за себя — не нужно лезть в комментарий, чтобы вспомнить, что означает `2`. Это база для [стейт-машин](/ru/lessons/st-tipovye-bloki-i-patterny), с которых строится почти любая последовательная логика на объекте.

> [!ВАЖНО] Не путай `ARRAY OF STRUCT` (массив однотипных объектов, как в примере с приводами) со **вложенной структурой** (`STRUCT` внутри `STRUCT`, когда у объекта есть логическая подгруппа полей, например `ST_Motor.diagnostics.last_fault_code`). Оба приёма законны и часто комбинируются — выбор зависит от того, повторяется объект (`ARRAY`) или у одного объекта просто много уровней данных (вложенный `STRUCT`).

## Когда что использовать

| Инструмент | Решает задачу | Пример |
|---|---|---|
| `ARRAY` | один тип данных повторяется N раз | 5 приводов, 20 ячеек рецепта |
| `STRUCT` | у одного объекта много разнородных полей | один привод: скорость + ток + флаги |
| `ARRAY OF STRUCT` | оба случая сразу — типовой промышленный паттерн | 5 приводов, у каждого свой набор полей |
| `ENUM` | конечный список именованных вариантов вместо чисел | режимы, состояния стейт-машины |

## Мост к первоисточнику

Массивы, структуры и перечисления — не изобретение CODESYS, а часть [ГОСТ Р МЭК 61131-3-2016](https://allgosts.ru/25/040/gost_r_mek_61131-3-2016): раздел про производные типы данных описывает их ровно так же для Siemens, Rockwell и любой другой МЭК-совместимой среды. Синтаксис объявления может чуть отличаться по вендору (например, где именно создавать DUT), но сама идея «свой тип данных вместо голых переменных» — стандарт, и на собеседовании про другой ПЛК у тебя спросят именно её, а не конкретные меню CODESYS.

## Задание

Опиши на ST структуру данных для участка с **тремя однотипными дозаторами** (компонент любой отрасли: сыпучий продукт, жидкость, что угодно с задачей «отмерь и подай»):

1. Заведи `TYPE ST_Dosator` с полями: `target_kg : REAL` (уставка), `current_kg : REAL` (текущая масса), `dosing : BOOL` (идёт дозирование), `ready : BOOL` (готов к следующему циклу).
2. Заведи `E_DosatorState` — перечисление из состояний `State_Idle`, `State_Dosing`, `State_Done`, `State_Fault`.
3. Объяви `dosators : ARRAY[1..3] OF ST_Dosator` и по одной переменной состояния `E_DosatorState` на каждый (массивом или отдельно — обоснуй свой выбор в одном предложении).
4. Опиши словами (без цикла — это тема следующей статьи), как программа узнает, что **все три** дозатора одновременно в состоянии `State_Done`.

Критерий самопроверки: перечитай пункт 3 — если выбрал `ARRAY[1..3] OF E_DosatorState`, объясни, почему это ARRAY, а не три отдельные переменные (подсказка: тот же довод, что и для `conveyors` в примере статьи).
