FUNCTION, FUNCTION_BLOCK и PROGRAM в Structured Text — как разложить программу на переиспользуемые блоки вместо одного файла на пару тысяч строк.
---
## Ментальная модель: три разных «кирпича», и они не взаимозаменяемы

Ты уже пользовался готовыми функциональными блоками — [таймерами и счётчиками](/ru/lessons/taymery-schetchiki-tipovye-bloki) TON, CTU. Настало время понять, из чего они сделаны, и научиться писать свои. В МЭК 61131-3 есть три вида программных единиц (POU — programme organization unit), и разница между ними не формальность, а вопрос «помнит ли блок что-то между сканами»:

| | Есть память между сканами? | Сколько экземпляров? | Что возвращает |
|---|---|---|---|
| **FUNCTION** | нет — чистый расчёт | не создаёт экземпляров, вызывается напрямую | ровно одно значение через имя функции |
| **FUNCTION_BLOCK** | да — у каждого экземпляра своя память | сколько нужно (каждый — отдельная переменная-экземпляр) | ноль и более значений через `VAR_OUTPUT` |
| **PROGRAM** | да | ровно один (singleton) во всём проекте, привязан к задаче в Task Configuration | не «возвращает», а исполняется как единица |

## FUNCTION: чистый калькулятор

`FUNCTION` не хранит ничего между вызовами — один и тот же набор входов всегда даёт один и тот же результат. Значение возвращается через **имя самой функции**, а не через отдельную выходную переменную:

```st
FUNCTION ScaleAnalog : REAL
VAR_INPUT
    raw_value          : INT;
    raw_min, raw_max    : INT;
    eng_min, eng_max    : REAL;
END_VAR
ScaleAnalog := eng_min +
    (INT_TO_REAL(raw_value - raw_min) / INT_TO_REAL(raw_max - raw_min))
    * (eng_max - eng_min);
```

Вызывается как обычное выражение — используется прямо в присваивании:

```st
level_m := ScaleAnalog(level_raw, 0, 32767, 0.0, 3.0);
```

Формула масштабирования 4–20 мА, которую ты писал вручную в [первой статье про ST](/ru/lessons/structured-text-st), одной строчкой превращается в переиспользуемую `FUNCTION` — теперь она пишется один раз и вызывается для любого аналогового сигнала на объекте, а не копипастится в каждый POU.

> [!ВАЖНО] `FUNCTION` **не может** содержать внутри себя экземпляр `FUNCTION_BLOCK` (например, таймер `TON`) — потому что у неё в принципе нет памяти между вызовами, а у экземпляра блока память обязана быть. Нужен таймер, счётчик или любая другая логика «с памятью» внутри твоего блока — пиши `FUNCTION_BLOCK`, не пытайся впихнуть это в `FUNCTION`. Это классический вопрос на понимание разницы на собеседовании.

## FUNCTION_BLOCK: прибор с собственной памятью

`FUNCTION_BLOCK` — это уже знакомый тебе `TON` или `CTU`, только свой. У него есть внутреннее состояние, и поэтому его **обязательно объявляют экземпляром** — переменной конкретного типа блока — прежде чем вызывать:

```st
FUNCTION_BLOCK FB_Dosator
VAR_INPUT
    start       : BOOL;
    target_kg   : REAL;
    current_kg  : REAL;   // масса с датчика — блок её только читает
END_VAR
VAR_OUTPUT
    dosing : BOOL;
    ready  : BOOL;
END_VAR
VAR
    state : E_DosatorState;   // тип из статьи про перечисления — своя память экземпляра
END_VAR

// тело блока: логика состояний живёт здесь,
// подробно разберём в статье про паттерны
```

Три дозатора с линии из прошлой статьи — это **три независимых экземпляра** одного и того же блока, каждый со своей памятью:

```st
VAR
    dos1, dos2, dos3 : FB_Dosator;
END_VAR

dos1(start := start_btn1, target_kg := 12.5);
dos2(start := start_btn2, target_kg := 8.0);
```

Ровно то же правило, что ты уже видел для таймеров: **один физический процесс = один экземпляр**. `dos1` и `dos2` работают независимо, даже если код внутри `FB_Dosator` написан один раз.

## PROGRAM: верхний уровень, ровно один экземпляр

`PROGRAM` — точка входа, привязанная к конкретной циклической задаче в Task Configuration. В отличие от `FUNCTION_BLOCK`, его нельзя объявить переменной и создать несколько экземпляров — он в проекте **один по определению**, и именно он вызывает функциональные блоки и функции (а не наоборот — блок не может вызвать программу изнутри себя).

```st
PROGRAM PLC_PRG
VAR
    dos1, dos2, dos3 : FB_Dosator;
    level_m          : REAL;
END_VAR

level_m := ScaleAnalog(level_raw, 0, 32767, 0.0, 3.0);
dos1(start := start_btn1, target_kg := 12.5);
```

## VAR_IN_OUT: когда блок должен и читать, и менять чужую переменную

`VAR_INPUT` копирует значение внутрь блока, `VAR_OUTPUT` копирует результат наружу — это **копии**, изменение одной не влияет на другую. `VAR_IN_OUT` передаётся **по ссылке**: блок работает напрямую с переменной вызывающего кода, а не с её копией. Используют, когда блок должен изменить структуру или массив, переданный ему, — например, функция сортировки массива приводов по приоритету работает через `VAR_IN_OUT`, а не возвращает копию всего массива.

> [!ПРИМЕР] Разница на практике: если `raw_value` в `ScaleAnalog` был бы `VAR_IN_OUT`, а функция по ошибке присвоила бы ему что-то внутри тела — это изменило бы переменную `level_raw` вызывающего кода, хотя по смыслу задачи это должно быть только чтение. Используй `VAR_INPUT` там, где блок только читает, и `VAR_IN_OUT` — только когда ему реально нужно писать в переменную вызывающего.

## TIA Portal SCL: где совпадает, а где нет

Siemens TIA Portal — второй по частоте пункт в вакансиях после CODESYS. Хорошая новость: бо́льшая часть того, что ты выучил, переносится буквально:

| Что | CODESYS | TIA Portal (SCL) |
|---|---|---|
| Таймер | `t : TON; t(IN := x, PT := T#5S);` | то же самое: `t : TON; t(IN := x, PT := T#5S);` |
| Массив | `arr : ARRAY[1..5] OF INT; arr[1]` | то же самое: `arr : Array[1..5] of Int; arr[1]` |
| Объявление FB | `FUNCTION_BLOCK FB_Dosator VAR_INPUT ... END_VAR` | те же секции `VAR_INPUT`/`VAR_OUTPUT`, но: переменные внутри тела читаются только через `#` (`#start`, не `start`), а память экземпляра — не просто переменная, а отдельный объект проекта, **instance-DB** |

Расхождение сосредоточено ровно в объявлении и вызове FB — язык вычислений (`IF`/`CASE`/циклы/таймеры/массивы) одинаков что в CODESYS, что в TIA Portal. Готовясь к собеседованию в компанию на Siemens, не переучивай язык заново: освой две конкретные привычки — `#` перед именем переменной и то, что за каждым экземпляром блока в дереве проекта стоит реальный DB, а не абстрактная память в фоне.

## Мост к первоисточнику

[ГОСТ Р МЭК 61131-3-2016](https://allgosts.ru/25/040/gost_r_mek_61131-3-2016) закрепляет именно это разделение — `FUNCTION`/`FUNCTION_BLOCK`/`PROGRAM` называются одинаково в любой МЭК-совместимой среде (CODESYS, TIA Portal, Studio 5000), меняется только то, где в конкретной IDE создаётся новый POU и как настраивается его привязка к задаче. Разница «с памятью / без памяти», однажды понятая, переносится на любой контроллер без переобучения.

## Задание

Перепиши формулу масштабирования из своего задания к первой статье про ST в виде `FUNCTION ScaleAnalog`, как в примере этой статьи. Затем:

1. Заведи `FUNCTION_BLOCK FB_Dosator` с полями `start`, `target_kg`, `current_kg` (вход) и `dosing`, `ready` (выход) — пока без тела логики, просто корректная декларация.
2. Объяви три экземпляра `FB_Dosator` для линии из трёх дозаторов.
3. Письменно объясни (2–3 предложения): что пошло бы не так, если бы вместо трёх экземпляров ты завёл один `FB_Dosator` и пытался переиспользовать его для всех трёх дозаторов по очереди.

Критерий самопроверки: в пункте 3 твой ответ должен объяснять именно **память экземпляра** — если ответ не упоминает, что состояние блока перепуталось бы между дозаторами, перечитай раздел про `FUNCTION_BLOCK` ещё раз.
